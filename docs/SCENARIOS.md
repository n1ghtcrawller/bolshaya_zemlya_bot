# Бот «Большая Земля» — сценарии работы

Записка по всем пользовательским и административным сценариям. Названия кнопок — дословно из UI (включая фирменное «диллер» через два «л»).

**Роли:** `client` · `dealer` · `sales` · `head_of_sales` · `marketing` · `head_of_marketing` · `admin`.
Новый пользователь при первом контакте с ботом автоматически создаётся с ролью **client**.

---

## 1. Общая механика

| Что | Как работает |
|---|---|
| Вход | `/start` → приветствие → меню по роли: 🟢 Клиент, 🟠 Диллер, 🔵 Sales / HeadOfSales, 🟣 Маркетинг / HoM, ⚙️ Админ |
| Онбординг | Любой апдейт от нового человека создаёт запись в `users` с ролью `client`; роль кэшируется в Redis на `ROLE_CACHE_TTL` (30 мин) |
| Отмена | `/cancel` или reply-кнопка «✖️ Отмена» — сбрасывает любой пошаговый сценарий (FSM) |
| Навигация | «◀️ В меню» — возврат в главное меню роли, сбрасывает текущий сценарий |
| Пропуск шага | В необязательных полях ввод «-» пропускает шаг |
| Доступ | Каждый раздел закрыт фильтром ролей — чужие кнопки/команды просто не срабатывают |

## 2. 🟢 Клиент

Меню: «📚 Каталог», «🔍 Подобрать технику», «📝 Оставить заявку», «📍 Найти диллера», «🔧 Сервис и запчасти», «💬 Чат с менеджером», «📞 Заказать звонок», «📋 Мои заявки», «👤 Профиль».

### 2.1 Каталог / Подобрать технику
Категории → страница товаров (по 5, с пагинацией ◀️ ▶️) → карточка товара (фото, цена «по запросу» если не указана, характеристики). «🔍 Подобрать технику» — тот же каталог с другим заголовком (подбор по параметрам — в планах).
Из карточки товара: **«📝 Оставить заявку на этот товар»** — запускает обычную заявку, в комментарий автоматически подставляется «Интересует товар «{название}» (#id)», к лиду привязывается `product_id`.

### 2.2 Оставить заявку (лид `request`)
Шаги: имя (мин. 2 символа) → телефон (кнопкой «📱 Поделиться контактом» или текстом) → комментарий (или «-») → экран подтверждения «✅ Подтвердить / ✖️ Отмена».
Результат: заявка `#id` со статусом **новая**; телефон сохраняется в профиль клиента; **при включённом Битриксе лид ставится в очередь отправки в CRM**.

### 2.3 Найти диллера
Регион → список дилеров → карточка (компания, адрес, телефон, специализация). Действия: «💬 Написать в TG» (прямая ссылка), «📝 Оставить заявку», «📞 Заказать звонок» — оба с пометкой «Через карточку диллера: …» в комментарии. ⚠️ Заявка при этом **не назначается** на дилера автоматически — маршрутизирует sales.
В справочник попадают только активные дилеры с заполненным регионом профиля.

### 2.4 Сервис и запчасти (отдельная ветка, не лид)
Тип обращения («🛡 Гарантия» / «🔧 Ремонт» / «🔩 Запчасти» / «📋 Другое») → модель техники (или «-») → описание проблемы → телефон.
Результат: сервисное обращение в общую очередь дилеров (статус **новое**). Тоже уходит в Битрикс как лид типа «Сервис / запчасти».

### 2.5 Чат с менеджером (лид `consultation`)
Тема обращения → телефон. Имя не спрашивается — берётся из Telegram-профиля. Живого чата нет: создаётся обращение, менеджер связывается сам.

### 2.6 Заказать звонок (лид `callback`)
Телефон → удобное время/тема (или «-»). Без экрана подтверждения.

### 2.7 Мои заявки / Профиль
«📋 Мои заявки» — список своих лидов со статусами (🆕 новая / ⚙️ в работе / 📨 передана диллеру / 🔒 оставлена у sales / ✅ выполнена / ❌ отклонена) и карточками. Сервисные обращения в этом списке **не** показываются.
«👤 Профиль» — только просмотр (имя, телефон, регион, организация, email); телефон появляется автоматически после первой заявки.

## 3. 🟠 Диллер

Меню: «📥 Новые лиды», «📚 Продающие материалы», «🔧 Сервисные обращения», «📊 Статистика», «👤 Профиль».

### 3.1 Новые лиды
Видит **только назначенные на него** лиды в статусах «передана диллеру» и «в работе». Карточка → действия:
- «⚙️ Взять в работу» → статус **в работе**
- «✅ Выполнено» → **выполнена**
- «❌ Отклонить» → **отклонена**

Уведомления клиенту/сейлзу не отправляются — все смотрят свои списки.

### 3.2 Продающие материалы
5 разделов: «📕 Каталоги», «🖼 Фото / Видео», «📊 Презентации», «📝 Шаблоны», «🎓 Обучение по продукту». Видны только **одобренные** материалы; файл приходит прямо в чат (по Telegram file_id, по 5 на страницу).

### 3.3 Загрузить на согласование
«✍️ Загрузить на согласование» → категория → файл (документ/фото/видео/GIF) → название → описание (или «-»).
Материал получает статус **pending** и попадает в очередь «🛡 Модерация материалов» у маркетинга. До одобрения другим дилерам не виден.

### 3.4 Сервисные обращения
Видит **свои + общую очередь без назначенного дилера**. Действия: «⚙️ Взять в работу» (закрепляет за собой, пропадает у остальных) → «✅ Закрыть» / «❌ Отклонить» (только назначенный дилер).

### 3.5 Статистика и профиль
«📊 Статистика» — счётчики своих лидов по статусам. «👤 Профиль» — редактирование 6 полей по одному: телефон, компания, регион, адрес, специализация, «о компании» («-» очищает поле). ⚠️ Регион обязателен, чтобы дилер появился в справочнике «Найти диллера».

## 4. 🔵 Sales и HeadOfSales

Меню: «📥 Новые лиды», «⚙️ В работе», «📨 Переданы диллеру», «📍 Найти диллера», «🤖 ИИ-помощник». У HeadOfSales дополнительно: «👔 Очередь согласований».

### 4.1 Жизненный цикл лида

```
Клиент создаёт заявку/консультацию/звонок ........ новая
        ▼ Sales: «⚙️ Взять в работу»
        (общая очередь FIFO, первый успевший)      в работе + закрепление за sales
        ▼ Sales: «📨 Передать диллеру» → регион → дилер → карточка:
   ├─ «✅ Передать сюда лид» ..................... передана диллеру
   ├─ «👔 Запросить согласование руководителя» ... заявка HeadOfSales (pending)
   │        ├─ HoS «✅ Одобрить» ................. передана диллеру
   │        └─ HoS «❌ Отклонить» ................ остаётся у sales (в работе)
   └─ «🔒 Оставить лид у себя» ................... оставлена у sales
        ▼ Диллер: «⚙️ Взять в работу» → «✅ Выполнено» / «❌ Отклонить»
```

### 4.2 Ключевые правила
- «📥 Новые лиды» — общая очередь всех неразобранных лидов (видят все sales одинаково). Гонка решается просто: второй нажавший получает «Этот лид уже забрал другой Sales».
- Передавать/оставлять/запрашивать согласование может **только владелец** лида (кто взял в работу).
- Кнопка «👔 Запросить согласование руководителя» появляется **только если в БД есть активный head_of_sales**. По лиду может быть только один открытый запрос.
- «❌ Отклонить» доступно и из общей очереди (лид закрепляется за отклонившим), и по своему лиду.
- «📍 Найти диллера» вне передачи лида — просто справочник (карточка + «💬 Написать в TG»).

### 4.3 ИИ-помощник
Диалоговый режим: вопрос → «🤖 Думаю...» → подсказка (через n8n). Можно задавать вопросы подряд; выход — «✖️ Отмена» или «◀️ В меню». При недоступности n8n — «ИИ-помощник временно недоступен», бот не падает.

### 4.4 HeadOfSales: очередь согласований
«👔 Очередь согласований» → список запросов (`#запрос · лид · от sales → диллеру`) → карточка с данными лида → «✅ Одобрить» (реальная передача лида дилеру) / «❌ Отклонить» (лид остаётся у sales). Повторное решение по обработанному запросу блокируется.
⚠️ Уведомления sales-автору о решении нет — он видит результат в списках «В работе» / «Переданы диллеру».

## 5. 🟣 Маркетинг / HeadOfMarketing / ⚙️ Админ

Все три роли видят **одно меню**: «📊 Дашборд», «👥 Пользователи», «📚 Материалы (загрузка)», «📣 Рассылки», «📝 Контент», «🎪 Выставки», «📦 Каталог продукции», «🛡 Модерация материалов», «🤖 ИИ-помощник (Выставки)».

Отличия:
| Возможность | marketing | head_of_marketing | admin |
|---|---|---|---|
| Одобрять контент и материалы | только если HoM нет в БД (fallback) | ✅ | ✅ |
| Удалять пользователей | ❌ | ❌ | ✅ |
| Всё остальное меню | ✅ | ✅ | ✅ |

### 5.1 Дашборд
- «📋 Сводка» — пользователи по ролям + лиды по статусам
- «📍 По диллерам» — топ-10 дилеров по назначенным лидам с разбивкой по статусам
- «📦 По продуктам» — топ-10 товаров по заявкам (связь появляется при заявке из карточки товара)

### 5.2 Пользователи (управление ролями)
Роль-фильтр → список → карточка → «✏️ Сменить роль» → любая из 7 ролей. Кэш роли в Redis инвалидируется автоматически — новая роль действует со следующего сообщения пользователя.

**Удаление (только admin):** в карточке появляется «🗑 Удалить пользователя» → экран подтверждения → «🗑 Удалить». Защиты: нельзя удалить себя; для не-админов кнопки нет. Каскадно удаляются профили, заявки, сервисные обращения пользователя; авторство материалов/контента/рассылок обнуляется, сами записи остаются.

### 5.3 Материалы (загрузка)
Категория → файл → название → описание. Материал публикуется **сразу** (без модерации) и виден всем дилерам.

### 5.4 Рассылки
«✍️ Новая рассылка»: текст (или «-») → медиа (или «-»; пустую рассылку не даст создать) → сегмент («Все пользователи» или конкретная роль, с подсчётом получателей) → подтверждение → отправка **через n8n**. История: «📜 История» (последние 20, статусы draft/queued/sent/failed). При недоступности n8n рассылка помечается `failed` с текстом ошибки.

### 5.5 Контент
4 раздела: «🗓 Контент-план», «💡 Идеи», «📍 Адаптации по регионам», «⏰ Отложка» + очередь «🛡 На согласовании».
Создание: тип → заголовок → тело → регион → дата публикации (ДД.ММ.ГГГГ ЧЧ:ММ, UTC) → медиа → «📝 Черновик» или «📤 На согласование».
Статусы: ✍️ черновик → 🛡 на согласовании → ✅ согласовано / ❌ отклонено; ⏰ запланирована → 📢 опубликована; 🗄 в архиве.
Одобрение/отклонение — по политике HoM (см. таблицу выше). Записи со статусом «запланирована»/«согласовано» и датой в прошлом **автоматически публикует** фоновый воркер (см. §6.4).

### 5.6 Выставки
«📅 Ближайшие» (список + карточки) и «➕ Добавить выставку»: название → локация → дата начала → дата окончания → продукты → описание.

### 5.7 Каталог продукции
«➕ Категория» (название, slug генерируется) и «➕ Товар» (категория → название → краткое описание → полное → цена текстом → характеристики → фото). Товар сразу виден клиентам. Редактирования/удаления в UI пока нет — только через SQL.

### 5.8 Модерация дилерских материалов
«🛡 Модерация материалов» → очередь pending → карточка (файл приходит в чат) → «✅ Одобрить» (виден всем дилерам) / «❌ Отклонить». Права — по политике HoM. Автор-дилер уведомление не получает.

### 5.9 ИИ-помощник (Выставки)
Как у Sales, но по тематике выставок (свой n8n-webhook).

## 6. ⚙️ Управление системой (админ/devops)

### 6.1 Запуск

**Вариант A — всё в Docker:**
```powershell
copy .env.example .env   # заполнить BOT_TOKEN
docker compose up -d --build
docker compose logs -f bot
```
Поднимаются `bz_postgres`, `bz_redis`, `bz_bot`; миграции применяются автоматически. Требуется внешняя docker-сеть n8n (`n8n-compose-file_default`).

**Вариант B — бот локально:**
```powershell
pip install -e . ; copy .env.example .env
docker compose up -d postgres redis
alembic upgrade head
python -m bot
```

Изменение `.env` требует рестарта процесса (конфиг кэшируется).

### 6.2 Назначение первого админа
```sql
UPDATE users SET role = 'admin' WHERE telegram_id = 123456789;
```
```bash
redis-cli DEL user:role:123456789    # или подождать 30 мин (TTL кэша)
```
Пользователь должен предварительно сделать `/start` (иначе записи в `users` нет). Дальше роли назначаются через UI «👥 Пользователи» — там кэш сбрасывается сам.

В Docker: `docker exec -it bz_postgres psql -U bot -d bolshaya_zemlya`, `docker exec -it bz_redis redis-cli`.

### 6.3 Интеграция Bitrix24 (сбор лидов)

Каждый лид клиента (заявка/консультация/звонок/сервис) при `BITRIX_ENABLED=true` **гарантированно** доставляется в Bitrix24 как Лид (`crm.lead.add`):

```
лид создан → строка в bitrix_outbox (pending, та же транзакция)
    → воркер раз в 60 с → отправка в Bitrix
        ├─ успех → sent + bitrix_lead_id
        └─ ошибка → attempts++, повтор с backoff (60с → 2м → 4м … cap 1ч)
              после 10 неудач → failed (нужно ручное вмешательство)
```

- **Тип обращения** пишется в `SOURCE_DESCRIPTION` («Заявка» / «Консультация» / «Обратный звонок» / «Сервис / запчасти») и опционально в UF-поле.
- **Ответственные** — round-robin «по очереди» из `BITRIX_ASSIGNED_BY_IDS` (сейчас: Козырев 25 → Воронцов 23 → Котельников 19 → Лузянин 21). Пусто → владелец вебхука.
- Настройка на стороне Bitrix: CRM → Разработчикам → Другое → **Входящий вебхук** с правом `crm`; URL до кода (без метода) в `BITRIX_WEBHOOK_URL`.
- При `BITRIX_ENABLED=false` очередь не пишется, воркер не стартует.

**Диагностика очереди:**
```sql
SELECT status, count(*) FROM bitrix_outbox GROUP BY status;

SELECT id, source_type, source_id, attempts, last_error
FROM bitrix_outbox WHERE status = 'failed' ORDER BY updated_at DESC;

-- переотправить неудачные:
UPDATE bitrix_outbox
SET status='pending', attempts=0, next_attempt_at=now(), last_error=NULL
WHERE status='failed';
```

### 6.4 Автопостинг контента
Воркер раз в `PUBLISHER_INTERVAL_SECONDS` (60 с) берёт контент-записи в статусах «запланирована»/«согласовано» с датой публикации ≤ сейчас и шлёт в n8n (`N8N_WEBHOOK_CONTENT_PUBLISH`). Успех → «опубликована». При недоступности n8n — повтор на следующем тике (бесконечно, без счётчика). Отключение: `PUBLISHER_ENABLED=false`.

### 6.5 n8n: 4 интеграции
| Webhook | Что делает |
|---|---|
| `N8N_WEBHOOK_SALES_ASSISTANT` | ИИ-помощник Sales |
| `N8N_WEBHOOK_EXPO_ASSISTANT` | ИИ-помощник по выставкам |
| `N8N_WEBHOOK_BROADCAST` | Фактическая доставка рассылок |
| `N8N_WEBHOOK_CONTENT_PUBLISH` | Автопостинг в канал |

Готовые workflow — в `n8n/workflows/`. Авторизация — `N8N_AUTH_HEADER` (кладётся в заголовок `Authorization` целиком). При недоступности n8n ничего не падает: ассистенты пишут «временно недоступен», рассылки — `failed`, автопостинг ретраит.

### 6.6 Мониторинг (structlog)
`LOG_LEVEL` + `LOG_JSON=true` для машинного разбора. Ключевые события:

| Событие | Значение |
|---|---|
| `bot_started` / `bot_stopping` | старт/остановка |
| `client_request_created`, `service_request_created` | новый лид/обращение |
| `bitrix_lead_sent` | лид доставлен в CRM |
| `bitrix_lead_retry` | временный сбой, будет повтор (INFO) |
| `bitrix_lead_failed` | **лид не доставлен, попытки исчерпаны — алертить** |
| `content_published` / `content_publish_failed` | автопостинг |
| `broadcast_sent` / `broadcast_send_failed` | рассылки |
| `user_role_changed`, `user_deleted` | аудит админ-действий |

### 6.7 Переменные окружения (группы)
`BOT_*` (токен), `POSTGRES_*`, `REDIS_*`, `ROLE_CACHE_TTL`, `N8N_*` (5 переменных + auth), `BITRIX_*` (10 переменных, см. `.env.example`), `PUBLISHER_*`, `LOG_*`. Полная таблица — в [README.md](../README.md).

## 7. Известные ограничения и нюансы

- **Уведомлений между ролями нет** — вся коммуникация pull-моделью (каждый смотрит свои списки). Sales не узнаёт о решении HoS, дилер — о переданном лиде, дилер-автор — о результате модерации, пока не откроют раздел.
- **«🔒 Оставленные у себя» лиды не видны ни в одном списке sales** — статус есть, пункта меню нет.
- У HeadOfSales после «◀️ В меню» показывается обычное sales-меню без кнопки очереди согласований — вернуть её можно через `/start`.
- Заявка «через карточку диллера» не привязывается к дилеру в БД — только текстовая пометка в комментарии.
- Текст «✖️ Отмена» на шагах свободного ввода (имя, тема, описание) может быть принят как введённое значение — надёжнее `/cancel`.
- Смена статусов не всегда перепроверяет текущий статус на сервере (защита — видимостью кнопок); одобрение HoS перезапишет лид, даже если sales уже распорядился им сам.
- Воркеры рассчитаны на **один процесс бота** — горизонтальное масштабирование без доработки грозит двойной отправкой.
- Редактирования каталога, выставок и контента после создания в UI нет — только создание (правки через SQL).
